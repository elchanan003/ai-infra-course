# 05 — Tutor answers

## Quiz
1. Retry = re-attempt the same request inside the same group (router picks again; may choose B); fallback = after retries are exhausted, move to a different GROUP; cooldown = bookkeeping that removes a failing deployment from the group for `cooldown_time`. Walk-through: request picks A (50 %) -> 500 -> retry picks A or B; with up to 2 retries the chance all 3 tries hit A is 1/8, so most requests succeed on B, a few see an error (no fallback configured). A's failures accumulate; a 500 only cools A down after more than `allowed_fails` (3) failures in the current minute (some classes like 429/401/404/408 cool immediately). Once cooled for 5 s, all traffic goes to B (no wasted retries); after 5 s A is retried, fails again and the cycle repeats, so a dead replica still receives occasional probe requests.
2. The engines already schedule requests (continuous batching); the gateway just needs an unbiased, cheap, stateless choice that works across several gateway replicas. Reactive strategies (least-busy, latency) need shared state, herd traffic onto the "fast" replica until it is slow (oscillation), and LLM latency is dominated by output length, not replica health, so the signal is noisy. Smarter routing (KV/prefix aware) belongs to inference-aware routers.
3. Two deployments of the group with `weight: 1` (canary) and `weight: 9` (stable), `simple-shuffle`, stable `model_info.id`s. Watch per-deployment success/failure/latency metrics (`litellm_deployment_*`, engine metrics). For n=500, p=0.1: mean 50, sigma sqrt(500*0.1*0.9)=6.7, normal range about 37-63 (2 sigma).
4. Context-length errors are 400 `ContextWindowExceededError`; the user gets the error unless a fallback list keyed by the requested group exists (on v1.106.4 a generic `fallbacks` entry also catches it; `context_window_fallbacks` is the explicit, safer list). A typo in the group key silently disables it. Add `context_window_fallbacks: [{chat: [chat-big]}]` pointing at a group whose window fits 90k (also check it really does), and `enable_pre_call_checks: true` so the router skips deployments whose window is too small before calling them (and so the long prompt goes straight to a fitting deployment).
5. Data leaves the premises (privacy/compliance, air-gap policy); answer quality/behaviour differs (prompts tuned for the local model, safety/format differences); cost and budget (SaaS bills real money, spend accounting), availability dependencies/egress rules, capacity of the fallback target; legal/ownership. Visibility: count fallbacks (`x-litellm-attempted-fallbacks` header, metrics), alert on the fallback ratio, log which model served, page on sustained fallback not on single events.
6. (a) 50*3e-6 + 40*6e-6 = 1.5e-4 + 2.4e-4 = 3.9e-4. (b) 120 * 3.9e-4 = 0.0468. (c) 0.05/3.9e-4 = 128.2: calls 1-128 total 0.04992 < 0.05 so the 129th is still admitted (spend so far < budget) and overshoots to 0.05031; the 130th gets 422. So 129 allowed.
7. HTTP 422, error type `budget_exceeded` (measured on v1.106.4; assert status class + type, not message). With parallel requests the in-memory spend counter is racy (observed erratic "Current cost" values) and many requests are admitted before spend updates, so overshoot and counts are unpredictable; test sequentially.
8. Self-hosted models have no built-in price; `model_info` costs default to 0 so spend = 0. Define internal prices: (1) from GPU TCO: hourly cost / sustained tokens per hour, split prompt vs completion; (2) mirror a reference SaaS price list scaled by a factor / flat showback rate per 1k tokens; (also per-team allocation of reserved GPUs).
9. Concurrency = rate x latency = 60/min * 20 s = 20 concurrent requests, more than the engine's 8 slots: it can monopolize it. `max_parallel_requests` protects the engine. With 8 slots and chat needing 6: `max_parallel_requests: 2` (plus TPM cap and RPM as secondary).
10. Chat: low rate, small growing prompts, 1 concurrent per user, latency sensitive. Agent: high rate, huge prompts (system + tools + history resent), many parallel subagents, retry/loop amplification, throughput oriented, runaway cost risk. Dedicated engine replicas/GPU pool is the only layer that protects the KV cache; limits only shed load.
11. In memory per gateway replica by default, so each replica has its own view; shared only if `router_settings.redis_host/redis_port/...` is configured. Rate limits, however, read counters through the cache layer, so they need `litellm_settings.cache` + `cache_params` (module 04); router Redis does not do that.
12. `stream_timeout`: time to first token/data of a stream (a hung engine that accepted the connection but produces nothing). Once bytes have been sent the status is 200; retry/fallback can no longer help, the client sees a truncated stream; only pre-first-byte failures are retried/fallen back.
13. Example: groups `chat` (A+B, simple-shuffle), `agent` (dedicated C or share with limits), `fim` (small fast model). Fallbacks: `chat -> chat-small` allowed; `agent` falls back only to itself (retry) or fails; `fim` -> none (stale autocomplete is worse than none) ; never agent -> chat. Limits: chat keys RPM; agent keys max_parallel + TPM + daily budget; fim keys high RPM, low TPM and tiny max_tokens. Alerts: gateway: 429/5xx ratio per key; router: deployment state/cooldown and fallback ratio; engine: KV% and queue time.
14. Capacity or health problem hidden by the fallback: the primary group is failing/cooled or overloaded most of the time. Check deployment state, error causes, cooldown settings; users got degraded answers silently (small model, other region, SaaS spend/privacy). Add alerts on fallback ratio, fix primary, and review whether the fallback target had enough capacity.

## Lab — expected answers
- 5.1 `routing_strategy: simple-shuffle`; `weight: 4` on A and `weight: 6` on B (any ratio 2:3); `model_info.id`. A band 28-52 of 100.
- 5.2 `router_settings.fallbacks: [{"ha": ["ha-backup"]}]`, `num_retries` >= 0, a finite `timeout`; healthy A leaves B untouched.
- 5.3 e.g. `allowed_fails: 0`, `cooldown_time: 30`, `num_retries: 3`; all 20 succeed (retried on B), A hit once. Measured live (3 runs each): `allowed_fails: 1` + `num_retries: 2` is flaky (A hit 3-4 times, 19/20 sometimes: cooldown is registered asynchronously, so 3 quick attempts can all land on A); `allowed_fails: 1` + `num_retries: 3` hit A 2-3 times. Defaults (3 fails/min) give A about 10 hits and errors.
- 5.4 prices into `model_info.input_cost_per_token/output_cost_per_token` for BOTH chat deployments (one forgotten = wrong spend half the time); `SPEND_20 = 20 * (prompt_tokens * in_price + completion_tokens * out_price)`; budget key via `max_budget`; 422 `budget_exceeded` after at most one overshoot.
- 5.5 `MAX_PARALLEL = S - R`; `AGENT_TPM` between normal rate (tokens/call x calls/min) and 10x; agent key with `max_parallel_requests` + `tpm_limit`, chat key RPM only; teams separate.
- 5.6 Planted fault: the fallback entry is keyed `small-chat`, a name no client or group uses (the 400 ContextWindowExceededError message prints `fallbacks=[{'small-chat': ['big']}]`). Fix: key `small` (optionally also `context_window_fallbacks: [{"small": ["big"]}]`). Measured on v1.106.4: a correctly keyed generic `fallbacks` entry also catches the context-window 400. Wrong: deleting `small`, routing everything to `big`.

## Common mistakes
- Weights under `router_settings` instead of `litellm_params.weight`; mixing `order` (priority) with weights.
- Fallback target is a *deployment id* instead of a *group name*.
- Prices set on one deployment only; stale restart; checking spend before the flush; expecting exact split counts.
- `allowed_fails` high and `cooldown_time` 5 so a dead replica still takes many probes; no retries so users see the errors.
- RPM-only agent limits; budget on the key instead of the team; forgetting `tpm_limit`.
- Testing budgets with parallel load.
- Writing `SPEND_20` by running the system instead of computing it.
