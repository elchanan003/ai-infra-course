# 03 — Tutor answers

## Quiz
1. It sets the fraction of *this GPU's total memory this one vLLM instance may claim* (weights + profiled activations + non-torch overhead + KV pool; what remains after the first three is the KV pool). Not KV-only; not a limit on other processes on the GPU (other processes' memory counts against free memory and can make startup fail); also not shared across instances (each instance has its own fraction). Default 0.92 in the pinned docs.
2. (a) `2 × 32 × 8 × 128 × 2 B` = 131,072 B = 128 KiB/token. (b) 8192 × 131,072 = 1,073,741,824 B = exactly 1 GiB. (c) fp8: 64 KiB/token, 0.5 GiB per 8k sequence.
3. Budget 0.9 × 40 = 36 GB; minus 16 + 3 = 19 → KV pool 17 GB = 17e9 / 131,072 ≈ 129,700 tokens ≈ 15.8 → **15** sequences of 8192 (the engine's "max concurrency" would print ~15.8x). FP8 KV: ~259,400 tokens, ~31 sequences. (Accept GiB-based variants: 36 GB = 33.5 GiB … state units.)
4. Per token 131,072 B; 49152 × 131,072 = 6 GiB (consistent). `N = 4.5 GiB / 131,072 B` = 4,831,838,208 / 131,072 = **36,864** (vLLM may round down to a block multiple). Fixes: lower `--max-model-len` to <= 36,864 (cost: shorter contexts supported; fine if product needs less); raise `--gpu-memory-utilization` (cost: less headroom, risk of OOM / startup refusal on a shared GPU); `--kv-cache-dtype fp8` (cost: small accuracy impact, kernel/hardware support); lower `--max-num-batched-tokens` (smaller activation peak; cost: slower prefill); quantize weights (frees weight memory, not KV); tensor parallel / bigger GPU (cost: hardware, comms).
5. Scroll up to the first `ERROR` block in the EngineCore: the root cause is the `ValueError` (KV) or `OutOfMemoryError`/"Free memory on device" message above it. The final RuntimeError is a generic wrapper; `Failed core proc(s): {}` carries no information.
6. Another process holds GPU memory on the second node (a monitoring agent, a second instance, a notebook) so free memory at startup < 0.98 × total. Error of the form "Free memory on device … on startup is less than desired GPU memory utilization (0.98 …). Decrease GPU memory utilization or reduce GPU memory used by other processes." Fix: set utilization <= free fraction minus headroom (e.g. ~0.90), or remove the other process; do not run at 0.98 anywhere (non-torch growth OOM).
7. The panel shows `0.62%` instead of 62% (metric is a 0..1 fraction; "1 means 100 percent"). Fix: unit `percentunit` or multiply by 100. Old name `vllm:gpu_cache_usage_perc` was removed (replaced by `kv_cache_usage_perc`), so queries on it return nothing.
8. The scheduler frees a running request's KV blocks (pool exhausted) and puts it back in the waiting queue; V1 recomputes: prompt + already generated tokens are prefilled again (prefix-cache hits may soften it). Throughput falls because compute is spent twice; GPU utilization counts busy time, not useful work. Counter: `vllm:num_preemptions_total` (rate), histogram `request_num_preemptions`.
9. KV usage approaches 1 first (it is the cause); then waiting > 0 and/or preemption rate > 0 (which one first depends on whether the seq cap or KV binds: with a high `max_num_seqs` preemptions come first and refill the queue); TTFT p95 last among these because it is the user-visible consequence of queue + re-prefill. Accept either order for waiting/preemptions with the right reasoning; TTFT must not be first.
10. total 100, rank 0.95 × 100 = 95 falls in bucket (0.75, 1.0] with cumulative 90 before and 6 inside: `0.75 + (95−90)/6 × 0.25` = 0.75 + 0.2083 = **~0.958 s**. Approximate because quantiles are linearly interpolated inside a bucket (assumes uniform distribution within it; accuracy limited by bucket width). `_sum/_count` is the mean; hides the tail (also not a quantile).
11. The sequence cap is binding (running == max_num_seqs, waiting > 0, KV only 48% used, no preemptions). First change: raise `--max-num-seqs` (e.g. 64 → ~100) because KV has room; check first: how many tokens KV holds vs. average sequence size (`kv_cache_size_tokens` / avg live tokens) so the new cap does not push KV to 1.0 and cause preemption; also ITL SLO has slack (bigger batch raises ITL). Alternative/also: scale out a replica.
12. Any three: prompts begin with a timestamp/request id/user name (prefix differs); prompt shorter than `block_size` (only full blocks hit; CPU build has block 128); prefix evicted between requests (low traffic + LRU pool churn); different `cache_salt`/LoRA id per tenant; different chat template/system prompt version per client; replicas behind a non-prefix-aware load balancer so the request lands on a replica without the blocks; caching disabled by a flag or unsupported config (e.g. some multimodal/hybrid models).
13. Attention heads (and KV heads) are sharded across GPUs; heads must divide evenly (8 KV heads: TP 1, 2, 4, 8; TP=3 errors). Weights and KV per GPU are each ~1/TP (so TP buys memory: it makes a model fit and enlarges the KV pool). It adds all-reduce communication each layer, so it is not linear speed-up, and over PCIe it can slow decode; prefer the smallest TP that fits plus replicas for scale.
14. Simulated: the engine (mock-vllm): memory arithmetic with real flag semantics and model geometry, real error strings and metric names, deterministic virtual-clock latency, faults. Real: nothing of the GPU path (optional real vLLM-CPU v0.31.0 fp32 exists). Do not use mock latency/throughput numbers or the activation estimate as capacity figures; production has real activation peaks, CUDA graphs, NCCL, throttling, fragmentation.

## Common mistakes
- Using GB and GiB interchangeably (1 GiB = 1.0737 GB); 8192 tokens x 128 KiB is exactly 1 GiB.
- Forgetting activations/overhead; treating the whole `util x total` as KV.
- Reading `kv_cache_usage_perc` as a percentage.
- Raising `max-num-seqs` to fix queueing without checking KV (-> preemptions).
- Computing p95 with `_sum/_count` or picking the bucket upper bound instead of interpolating.
- Believing TP always speeds things up; TP must divide KV heads.
- Lowering `--max-model-len` below the lab floor to "pass" (3.2 checks the floor).
