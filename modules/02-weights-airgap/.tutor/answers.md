# 02 — Tutor answers

## Quiz
1. Little-endian u64 `00 01 00 00 00 00 00 00` = 0x0100 = **256** bytes of JSON header. Tensor data begins at absolute offset 8 + 256 = **264**. `data_offsets: [begin, end]` are byte offsets relative to the start of the data buffer (i.e. relative to 264), end exclusive.
2. Pickle is a stack-machine program, and `GLOBAL`/`STACK_GLOBAL` can import any callable while `REDUCE` calls it with attacker-chosen arguments (`os.system("...")`, `builtins.exec`, `subprocess.Popen`); `OBJ`/`INST`/`NEWOBJ`/`BUILD` can construct objects and call `__setstate__`. Executing it happens during `load`, before you see a tensor. `weights_only=True` swaps in a restricted unpickler allowing only tensors/containers/primitives and an allow-list of globals (default since PyTorch 2.6): a mitigation with a history of bypasses, not a guarantee; and it does nothing for `trust_remote_code`, other pickle consumers (joblib, sklearn) or `weights_only=False` code paths.
3. Any three: deny-list scanners are incomplete and have been bypassed (new gadgets, odd archive layouts, extension tricks); the model may contain non-pickle executable content (remote code `.py`, tokenizers, Lambda layers); scanning ≠ provenance (the repo may be typosquatted/not the intended model); behavioural poisoning/backdoors are invisible to opcode scans; a scanner may skip or fail to parse a file and report "clean"; scan result applies to this exact hash only. Policy answer: safetensors-only + pinned commit + sandbox + no egress.
4. `models--ORG--NAME/{blobs/<etag>, refs/main, snapshots/<commit>/<file> -> ../../blobs/<etag>}`. Entries in `snapshots/` are symlinks; `blobs/` holds the bytes (named by sha256 for LFS files, git sha1 for small ones); `refs/main` is a text file containing the commit sha `main` currently points to. Dropping symlinks gives empty snapshot folders or duplicated/dereferenced copies, `hf`/transformers can no longer resolve revisions and offline loading fails ("file not found in cache"); use `tar`/`rsync -a` or `--local-dir`.
5. It makes the HF client refuse network access and resolve only from the cache (error if missing). It does not isolate the process: other libraries/telemetry (vLLM usage stats, tiktoken downloads, LiteLLM model-cost map, Open WebUI update checks, pip/apt, `trust_remote_code` code that fetches things), container image pulls, DNS lookups made by other components, or code in the image can still call out. Proof needs network isolation + tripwire + control.
6. `GET /api/models/{repo}/revision/{rev}` (info + commit sha + siblings); `GET /api/models/{repo}/tree/{sha}?recursive=true` (file list/sizes/oids); `HEAD /{repo}/resolve/{rev}/{path}` (size, ETag, commit header); `GET /{repo}/resolve/{sha}/{path}` (bytes, Range). Xet: `hf` defaults to the Xet protocol and requests a read token from `/api/models/{repo}/xet-read-token/{sha}`; a classic-API mirror doesn't implement it, so `HF_HUB_DISABLE_XET=1` forces plain resolve downloads.
7. `main` moves: a re-run (or new node) can pull different weights/tokenizer/chat template → irreproducible deployments, silent behaviour change, hashes no longer match the approved manifest. Pin the **commit sha** (and verify hashes). Without `--include` it downloads every file in the repo (ONNX, GGUF, TF, duplicates: several times the size you need), wasting hours/bandwidth/storage and pulling unreviewed file types into the pipeline.
8. Integrity: bytes were not corrupted in transit/storage. Authenticity: bytes are the ones the trusted party produced/approved. A hash fetched from the same place as the data proves only the former. The manifest (SHA256SUMS or a signed manifest) is produced on the connected side after download/scan, carried over a separate channel (or signed), and verified on the inside after transfer, again after storing in S3/OCI, and before load/deploy.
9. Two identities: RW (`Admin/Read/Write/List/Tagging`) for the sync pipeline only; RO (`Read,List`) for serving pods (secrets via k8s Secret, not baked into images). A PUT/DELETE with RO credentials returns **HTTP 403 `AccessDenied`**; wrong access key gives `InvalidAccessKeyId`/`SignatureDoesNotMatch` (403 too, but a different error code) — a key that "works for GET but not PUT" is a permissions problem, not a credentials typo. Bucket per environment, prefixes by commit, immutable once published.
10. ETag of a multipart upload is `md5(concat(md5(part_i)))-N`, and for single-part uploads is an MD5 (and may differ with SSE); never sha256. Store sha256 in object metadata (`x-amz-meta-sha256`) and/or a `manifest.json`/`SHA256SUMS` object next to the data, and verify after download.
11. Tag = mutable name; digest = immutable content address of a manifest. With the containerd image store a multi-arch local image may be pushed as only its single-platform manifest, so the registry digest ≠ the local index digest shown by `docker images --digests`. Record the digest returned by the registry (`Docker-Content-Digest` / `oras manifest fetch --descriptor`) and compare to the running container's image reference/`RepoDigests`; never to the local image `Id`.
12. S3: + shared/scalable, easy tooling and RO/RW identities, range reads/streaming loaders, cheap; − no content-addressed versioning by default, ETag semantics, separate access/audit system, need own manifest. OCI/ORAS: + digests/immutability built in, same registry/auth/replication/mirroring as images, easy promotion by tag/digest, K8s/KServe patterns; − registries tuned for many mid-size layers (huge blobs, timeouts), less direct streaming into engines, tooling maturity (ModelKit/ORAS), storage backend limits.
13. 10 Gb/s = 1.25 GB/s x 0.6 = 0.75 GB/s → 140 / 0.75 = **187 s (~3 min)** for one node. Eight at once from a 25 Gb/s NIC (3.125 GB/s x 0.6 = 1.875 GB/s shared): each gets ~0.23 GB/s → 1120 GB / 1.875 = **~597 s (~10 min)**. Design: cache once per node on NVMe (DaemonSet/prefetch), stagger rollouts, multiple S3 nodes/CDN/peer-to-peer (Dragonfly-style) distribution, faster server NIC, keep warm spares so cold start is not on the incident path.
14. (1) default bridge network has internet access: no isolation, nothing proves offline. (2) `meta-llama/Llama-3.1-8B-Instruct` is a repo id: the engine will try to download it; with the cache unmounted and offline=1 it simply fails ("not in cache"), or without offline it fetches (and the model is gated: needs a token). (3) The cache/model directory is not mounted: use `--model /models/<local dir>` + volume read-only. (4) `TRANSFORMERS_OFFLINE` is legacy; the Hub client uses `HF_HUB_OFFLINE`. (5) `--trust-remote-code` executes repo Python: never on unreviewed code, and may fetch more. (6) Image is a mutable tag (`vllm/vllm-openai` = latest): pin by digest from the internal registry. (7) Hidden phone-homes (`VLLM_NO_USAGE_STATS=1`, `DO_NOT_TRACK=1`), root user/writable rootfs. Any four.
15. Run the workload (startup + a completion) on an `internal: true` network whose DNS is the tripwire sink that logs every query; probes run inside the network. Evidence: tripwire hit counter/DNS log shows zero external names for the whole window while the completion succeeds (also keep the container's logs). Control: same workload without the offline settings (e.g. `-hf repo` / no `HF_HUB_OFFLINE`) must produce hits; otherwise a quiet wire might just be broken. The DNS log is authoritative because HTTPS requests never reach an HTTP sink (TLS to a fake IP fails) but the name lookup always precedes the connection and is logged.

## Common mistakes
- `hf download` without `--include`, or one `--include` with several space-separated patterns; leaving Xet on (404 on `xet-read-token`).
- Treating `main` as stable; comparing hashes against files fetched from the same mirror only.
- Scanner that executes/imports the file (canary appears), or that flags everything with `GLOBAL` (false positives on the benign checkpoints), or ignores `STACK_GLOBAL` (protocol 4+ files evade a GLOBAL-only scanner), or does not look inside zip members.
- Serving credentials = RW credentials; testing only GET.
- Reading the digest from `docker images` instead of the registry; comparing against local image id.
- Setting `HF_HUB_OFFLINE=1` but running on a normal network and declaring victory; no control run; looking at the HTTP sink log for HTTPS traffic.
- `HF_HOME` pointing at an empty dir with offline=1 (every load fails) or at the dir with symlinks stripped.
