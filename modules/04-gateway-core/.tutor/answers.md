# 04 — Tutor answers

## Quiz
1. client -> proxy: auth (key hash lookup, cached) -> pre-call checks (model access, budget, rpm/tpm/parallel; synchronous, can reject with 401/403/422/429) -> Router picks a deployment of the model group (sync) -> SDK translates and calls the backend (with retries/timeouts/fallback, sync) -> response streamed back. Asynchronous after the response: success/failure callbacks (spend computation + queue, Prometheus, Langfuse) and the periodic batch write to Postgres. Spend lag therefore exists; rejections do not lag.
2. `model_name` = alias clients use (contract with clients; several entries with the same name form a group). `litellm_params.model` = provider prefix + the name the backend knows (contract with the backend). Wrong `model_name`: clients get "model not found / 400" or a rename breaks all clients. Wrong `litellm_params.model`/prefix: `LLM Provider NOT provided`, or backend 404/"model does not exist" (vLLM served-model-name mismatch). Also missing `/v1` in `api_base` -> 404.
3. 401 = key missing/invalid/expired (authentication; check the key exists/hash, expiry, typo, header). 403 = key valid but model (or route) not allowed (`key_model_access_denied`; `/key/info` and `/team/info`). 429 = RPM/TPM/parallel limit (read `Limit type`, `retry-after`; fixed 60 s window). 422 = budget exceeded (`budget_exceeded` error type; key/team spend vs `max_budget`, `budget_duration` reset).
4. Both levels apply; a model must be allowed by key and team, so the key can call nothing useful: `chat` is denied by the team, `embed` by the key (effectively the intersection is empty). Debug: `/key/info` (models, team_id), `/team/info` (models), then fix the team list (not a wildcard on the key).
5. Only a SHA-256 hash of the key is stored; plaintext is shown once at generation. Lost key = issue a new one (and delete/block the old one, rotate in the secret store); it cannot be recovered. Keys in config.yaml: secrets in Git, no per-key limits/spend/revocation without redeploy, static; keys belong in the DB and a secret manager, and Git holds the issuing procedure.
6. About 18 RPM (3 x 6) in expectation (any one client could hit 6 on each replica). Global: `litellm_settings.cache: true` + `cache_params: {type: redis, host, port, supported_call_types: []}` (Valkey). `router_settings.redis_*` shares router state (cooldowns, usage-based routing) but the rate limiter reads counters through the cache layer; measured: 4 requests pass for limit 2 with router redis only, Valkey empty.
7. 2 requests. TPM is counted after the response with real `usage`: request 1 is admitted (counter 0), finishes at 600; request 2 is admitted (600 < 1000), finishes at 1200; request 3 is refused (1200 > 1000). So TPM can overshoot by up to one request; bound it with `max_tokens` and limits on input size.
8. Fixed window: requests at t=0,10,20 pass (3), t=30,40,50 get 429, at t=60 the window resets: 60,70,80 pass, 90-110 429, etc. -> a repeating pattern of 3 x 200, 3 x 429. A token bucket refilling 3/min (1 per 20 s) would allow roughly every second request (smoother: 200 at 0,10?,... ) - different pattern, no window-boundary reset. `retry-after: 60` is the conservative upper bound consistent with a fixed 60 s window (actual reset can be sooner).
9. (1) No `database_url` in the config / DB unreachable at start: keys only existed in memory or cannot be validated: check `docker logs`, `/key/list`, `psql` row count. (2) Wrong/changed DB (new empty volume, different DB name/user): row count 0, volume mounts. (3) Master key changed (admin calls 401) or `LITELLM_SALT_KEY` changed (encrypted credentials unreadable): compare env across deploys. (Also: restart reading a different config file.)
10. Encrypts stored provider credentials (and similar secrets) in the DB. Regenerating after data exists makes the previously encrypted values undecryptable (models/credentials stored in DB break); keep it constant in the secret store.
11. Backend: constant/duplicate response `id` makes SpendLogs primary-key collisions so rows are dropped while key spend still increments. Pipeline: batch-write lag (`proxy_batch_write_at`), or spend logs retention/cleanup deleting old rows, or queries filtering a different time zone/window; also failed requests are logged with spend 0 so counts differ. Any two sensible ones.
12. `/health` calls every configured backend (slow, costly, makes the gateway "unready" when one backend is sick, and spends tokens on cloud models). Use `/health/readiness` for readiness and `/health/liveliness` for liveness; monitor backends separately.
13. The published engine port is a bypass: no auth, limits, spend, audit, aliases; any client can saturate the GPU. Fix: engine only on an internal network/ClusterIP + NetworkPolicy allowing only the gateway; debug via `kubectl port-forward`/exec by operators, not a permanent exposed port.
14. `rpm_limit` is not enough: set `max_parallel_requests` (cap concurrency on the engine), `tpm_limit` (sustained tokens; agent requests are large), and `rpm_limit`; budget on the team (policy), limits on the key (protection). An agent with small RPM but huge prompts and long generations still hogs KV/GPU; parallel and TPM address the actual resource. Separate key (and team) from chat users.
15. Any four: mock backends with fixed usage; one host/1-2 replicas; plain HTTP, no TLS/ingress; `proxy_batch_write_at: 5`; open `/metrics/`; no Postgres HA/backups; one master key in env vs secret manager/SSO; published ports on 127.0.0.1; no NetworkPolicy; no spend-log retention; CPU models instead of GPUs.

## Lab — expected answers

Reference files will be in `.tutor/solution/` (phase 2). Draft expectations:
- 4.1 `model_list` with `openai/<name>` + `api_base: http://<svc>:8080/v1`, `model_info.id`, costs; `general_settings.master_key: os.environ/...`, `database_url: os.environ/DATABASE_URL`. 4.1.4 depends on `database_url`.
- 4.2 `/key/generate` `{"key_alias":"lab-chat-only","models":["chat"]}`; idempotent = delete by alias (or `/key/delete` with `key_aliases`) before generating. 403 on embed, 401 for garbage.
- 4.3 `rpm_limit: 2`; second key `tpm_limit` below 2 x tokens-per-response (e.g. 50 with 30-token usage): request 1 and 2 pass, request 3 refused; first passes because TPM is counted after the response. 429 body names `Limit type`.
- 4.4 `database_url` set; `KEYS_TABLE=LiteLLM_VerificationToken`; `KEY_ROWS` = live `select count(*)` (variant-bound, includes seeded extras and learner keys); `SPENDLOG_PK=request_id`; `LOST_ON_RESTART=rpm_counters` only (keys/spend logs are in Postgres, model_list is re-read from config; un-flushed spend is a caveat, not a category).
- 4.5 `litellm_settings: {cache: true, cache_params: {type: redis, host: valkey, port: 6379, supported_call_types: []}}`. Without `supported_call_types: []` identical requests may be served from cache (4.5.4 fails).
- 4.6 team created with `models:["chat"]`; key created with `team_id`, no key-level models. The team answers the access question.
- 4.7 team `lab-ds` models lacks `embed`: `/team/update` adding `embed` to the team list (narrowest). Wrong fixes: `models:["*"]` / `all-proxy-models` on key or team (4.7.2 fails: coder reachable), editing the key only.
- 4.8 direct call from the client network: `refused` (or timeout) ; gateway 200; `K8S_CONTROL=NetworkPolicy`; `BYPASS_LOSES=auth,rate_limits,spend,audit,aliases`.

## Common mistakes
- Forgetting `openai/` prefix or `/v1`; using host-published ports (`localhost:18011`) as `api_base` inside the container network.
- Restarting nothing after editing config.yaml; reading logs of the wrong replica.
- Putting `redis_host` only under `router_settings` (the headline pitfall); omitting `supported_call_types: []` (accidental response caching).
- 4.2 script not idempotent (duplicate alias error on second run); not writing `keys.env`.
- `sleep 2` instead of polling after sending traffic; asserting exact RPM recovery at 60 s.
- Using `models: ["*"]` to fix 403; fixing the key instead of the team.
- Answering KEY_ROWS from the starter docs or memory instead of the live DB count.
- Confusing 401/403/429/422 in the answers.
