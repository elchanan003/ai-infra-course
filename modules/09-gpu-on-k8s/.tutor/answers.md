# 09 — Answers (tutor only; never show unprompted)

## Quiz

1. Pod -> kubelet (device plugin `Allocate`) -> containerd + `nvidia` runtime handler -> Container Toolkit (CDI/hook injects `/dev/nvidia*`, libcuda, `nvidia-smi`) -> kernel driver -> GPU. Failures: driver (module not loaded/version too old: `nvidia-smi` cannot communicate; "CUDA driver version insufficient"); toolkit (runtime not configured: no `/dev/nvidia*`, `nvidia-smi` missing in the pod); device plugin (crashed/not scheduled: node has no `nvidia.com/gpu` allocatable, pods Pending `Insufficient nvidia.com/gpu`); GFD (not deployed: product/count labels missing, nodeSelector never matches).
2. Extended resources must be declared in `limits` (limits alone is enough); if only `requests` is given the API server rejects the pod (limits required; requests must equal limits). Reason: extended resources cannot be overcommitted or throttled; integers only because a device is an indivisible unit (fractions come from sharing: MIG/time-slicing change what one unit is).
3. The two *tainted* nodes are the GPU nodes (the untainted node reports Insufficient: it has no GPUs). Problem: the pod lacks a toleration for `nvidia.com/gpu=present:NoSchedule`. Fix: add `tolerations: [{key: nvidia.com/gpu, operator: Exists, effect: NoSchedule}]`. The TaintToleration filter runs before NodeResourcesFit, so a tainted GPU node that is also full is still reported as "untolerated taint"; after adding the toleration the message may change to `Insufficient nvidia.com/gpu`.
4. One pod runs (on A, using both free GPUs). The second is Pending: `0/3 nodes are available: 3 Insufficient nvidia.com/gpu.` B and C each have 1 free GPU but a pod cannot span nodes (fragmentation). Options: free a GPU on B or C to make a 2-GPU node, add a node, or run TP=1 if the model fits.
5. With `maxSurge` 25% (rounds up to 1) the new pod is created first but there is no free GPU: it stays Pending and the rollout stalls (old pod keeps serving, nothing progresses). Fix: `strategy: Recreate` (downtime) or `rollingUpdate: {maxSurge: 0, maxUnavailable: 1}` (also brief gap); or keep a spare node/GPU for surge.
6. No `/dev/shm` memory volume: default 64 MiB shared memory; mount `emptyDir: {medium: Memory}` at `/dev/shm` (or larger `sizeLimit`); docker equivalent `--shm-size`/`--ipc=host`.
7. Indexes can be re-enumerated after reboot or hot-plug; UUID is stable per physical GPU. The ticket gets the UUID (and serial number, host name, XID, timestamp).
8. (a) `max by (Hostname, gpu, UUID) (DCGM_FI_DEV_XID_ERRORS) > 0`. (b) `deriv(DCGM_FI_DEV_FB_USED[30m]) > 0` (threshold in MiB/s; add `and` a flat-traffic condition, or use `predict_linear(...[1h], 3600) > total`). (c) `DCGM_FI_DEV_GPU_TEMP > 85` with `for: 5m`. `> 0` stays firing as long as the last XID value stays non-zero (until driver/GPU reset), good for "node is unhealthy" state; `changes(...[5m]) > 0` only fires when the value changes (a new, different XID) and goes quiet after the window even though the GPU is still broken.
9. 13 and 31: application-class -> restart/investigate workload (wait); 48: drain (reset/RMA); 63: reset at next window (row-remap applied on reset), drain if repeated; 79: drain immediately; 94: contained -> restart the affected pod, watch recurrence; 95: drain + GPU reset (uncontained, other processes suspect). Before draining: replicas of the model elsewhere? PodDisruptionBudget? Spare GPU capacity for the evicted pods (scheduling will fail otherwise)? Gateway cooldown/fallback in place?
10. GPU_UTIL = fraction of time any kernel is running; a single small kernel can read 100% with most SMs idle; decode is memory-bound so GPU_UTIL is high while compute and KV room remain. Reverse case: a vLLM server holding 90% VRAM but waiting on requests shows ~0% util while being "allocated". Capacity: `vllm:num_requests_waiting`, `vllm:kv_cache_usage_perc`, running requests, TTFT/ITL; DCGM profiling fields (`PROF_SM_ACTIVE`, `PROF_DRAM_ACTIVE`).
11. 8 x 4 = 32 `nvidia.com/gpu`. A request for 2 gets two time slots (possibly on the same physical GPU), not 2x compute, and breaks the "unit = whole GPU" assumption; `failRequestsGreaterThanOne: true` rejects such requests. Main risk: no memory or fault isolation; second server OOMs (or makes the first OOM); latency jitter. Use `renameByDefault: true` to keep shared and exclusive pools separate.
12. MIG: hardware memory + fault isolation, rigid, changing the layout is disruptive (drain, reset). Time-slicing: no memory or fault isolation, trivial to enable, replicas count only. MPS: concurrent kernels, optional memory/SM limits, no fault isolation (one client crash can take all). (a) MIG; (b) time-slicing; (c) dedicated GPUs with TP.
13. `2g.20gb` is the minimum (15 GB weights leaves ~5 GB for KV, tight); `3g.40gb` comfortable. `1g.10gb` cannot hold it. Strategy `mixed` (resource names `nvidia.com/mig-1g.10gb`, `nvidia.com/mig-3g.40gb`).
14. Differences (any two): nobody reconciles the patched field (a real plugin owns and rewrites it; capacity follows real devices); no `/dev/nvidia*` in containers, no driver, `nvidia-smi` only fake; labels set by hand instead of GFD; no health checking (a dead GPU would not reduce capacity). The scheduler cannot tell it from real capacity: it only compares numbers and labels.
15. kind has no device plugin, so nothing reads the config; kubeconform + server-side dry-run prove only schema/acceptance by the API server. On a real cluster: confirm the plugin pod restarted and logs "Retrieving plugins"/config loaded, node `allocatable` shows replicas x GPUs, GFD labels `gpu.replicas` and `-SHARED` product, run two test pods, watch for CUDA OOM, and confirm exclusive pods do not land on shared GPUs (`renameByDefault`).

### Check yourself (theory.md)
1. Resource name typo (`gpus` vs `gpu`): the scheduler treats it as an unknown extended resource no node advertises. Confirm: `kubectl get pod -o jsonpath='{.spec.containers[*].resources}'` and compare with `kubectl get node -o json | jq '.status.allocatable'` keys.
2. A pod cannot span nodes; the 2 free GPUs are on different nodes (fragmentation). Options: free a GPU on one node, add a 2-GPU node, TP=1 or a smaller/quantised model, or a multi-node framework (pipeline/Ray/LeaderWorkerSet).
3. B (XID 79): cordon + drain immediately, reboot/reset, hardware ticket with UUID; check replicas elsewhere, PDB, spare GPU capacity. A (XID 31): application-class: restart/investigate the pod, watch recurrence across workloads.
4. GPU_UTIL only means a kernel was running (memory-bound decode); use `vllm:num_requests_waiting`, `vllm:kv_cache_usage_perc` (or profiling SM/DRAM active).
5. At 0.9 x 80 GB = 72 GB reserved per server, the second cannot allocate: CUDA OOM at start (or kills the first); time-slicing has no memory isolation. Alternatives: dedicated GPU each, MIG `3g.40gb` pair with smaller models, quantise (fp8/int4) to fit two, or one replica with more batching.

## Expected lab answers and common mistakes

Variant data lives in `.state/variant.env` (HOT_*, XID_*, INJ_*; created by `prepare-lab.sh A`, removed by `cleanup.sh`). Never show it to the learner; the learner derives it from `bin/smi` and the metrics.

- **9.1**: read the max-temperature row of `bin/smi A --query-gpu=index,uuid,temperature.gpu,memory.total,power.limit --format=csv`. Hot GPU = the one with util 85 in the variant (about 66 C vs 46-50 C for the others). Memory/power pair is unique per GPU (80 GB SXM 81920/400, 40 GB SXM 40960/400, 40 GB PCIe 40960/250, 80 GB PCIe 81920/300). Mistakes: answering GPU 0; GB instead of MiB; current draw instead of cap; index/UUID of different GPUs.
- **9.2**: reference rules in `.tutor/solution/prometheus/rules/dcgm-alerts.yml`. GpuXidError `> 0` with `for` <= 1m (state, not `changes()`); GpuTooHot `> 85` `for: 2m`; GpuEccUncorrected `increase(DBE[5m]) > 0` (SBE excluded); GpuMemoryLeak `predict_linear(FB_USED[10m], 7200) > FB_USED + FB_FREE` with `for`. Mistakes: `changes()` on XID; `deriv() > 0` (fires on slow drift, caught by the SLOW series); `for: 5m` on hot (fine) but on XID (caught by 2m eval); ECC via SBE; aggregation that drops UUID/Hostname (`sum`, `without`); no `reload`.
- **9.3**: the variant XID is one of 13/31/43 (wait) or 48/64/74/79/95 (drain); ACTION follows the class. The fault is on node A or B; XID 79 is only ever placed on node B, so `nvidia-smi` on A stays readable for 9.1. REASON: cites the class or code plus the pre-drain checks (replicas, PDB, spare GPUs). Mistakes: drain for application XIDs; reading only one node's metrics.
- **9.4**: `kubectl patch node N --subresource=status --type=json` with `add` of `/status/capacity/nvidia.com~1gpu` and `/status/allocatable/...`; `label --overwrite` x3; `taint --overwrite`. Verify runs it twice with different inventories (counts 3-5 and 2-4, nonce product strings), then idempotency. Mistakes: hard-coded numbers; capacity-only patch (works after the kubelet sync, ~10 s; verify polls 30 s); `taint` without `--overwrite` (second run fails: idempotency check); forgetting the control-plane must not be touched.
- **9.5**: limits only, toleration, exact product label. The two controls (4-GPU pod, no-toleration pod) are verify's. Mistakes: requests without limits (rejected by the API), mistyped product label (Pending: didn't match node affinity/selector).
- **9.6**: reference `.tutor/solution/k8s/timeslicing-cm.yaml`. Mistakes: nested YAML instead of a string under `data.any`; `renameByDefault` inside the resources entry; `replicas` as string; wrong namespace. Honesty: validated, not exercised; real check after applying is in theory 4.7.
- **9.7**: `limits.nvidia.com/gpu: 2`, `--tensor-parallel-size 2`, Memory emptyDir `/dev/shm`, `Recreate` or `maxSurge: 0`, A100 selector + toleration. Verify rolls a new revision (annotation change) and requires Running within 120 s; with default RollingUpdate the surge pod is Pending (`Insufficient nvidia.com/gpu`) and the check fails. Control: same template with nodeSelector `kubernetes.io/hostname: aiinfra-worker2` must be Pending on Insufficient.
- **T**: `nvidia.com/gpus` typo and the missing toleration; both must be fixed (one fix leaves the pod Pending with a different message). Pod spec is immutable for resources: delete and recreate (verify does `kubectl apply` on a clean namespace, so editing the file is enough). Disallowed: `nodeName` pinning, removing the taint, dropping the request.
- Part B scheduling tasks (9.5-T) are independent of 9.4: verify sets the reference topology (`.tutor/topology.yaml`, two tainted GPU nodes) itself.
