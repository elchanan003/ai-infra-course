# 00 — Tutor answers

## Quiz
1. Open WebUI, Aider = L1 clients (they only know base URL + key). LiteLLM = L2 gateway. Postgres (and Valkey) behind LiteLLM = **L2**: a datastore belongs to the layer that owns its state (keys, spend, limits) — not "infra" just because it is a database. llama.cpp container = L3 engine. SeaweedFS holding weights = L4 (platform storage feeding the engines). NVIDIA device plugin = L4 (makes `nvidia.com/gpu` schedulable). Rule: a component belongs to the layer whose job it performs. Qdrant (later) is application state beside L1/L2.
2. SSE: lines `data: {json}` separated by blank lines. First chunk usually carries only `delta.role`; then content deltas; one chunk has `finish_reason` (`stop`/`length`/`tool_calls`); if `stream_options: {"include_usage": true}` was sent, a final chunk with `choices: []` and `usage`; then literal `data: [DONE]`. Without `include_usage` there is no usage in the stream: the gateway has to estimate by counting or logs 0/partial tokens, so spend and TPM accounting are wrong or approximate.
3. Gains (any three): per-user/team keys and model allow-lists; RPM/TPM limits and budgets; spend logs/accounting; routing, load balancing, fallbacks; API normalisation across engines; central logging/metrics/callbacks; the engine never sees identities, and engines can move without clients changing. Costs: extra hop/latency; a new SPOF that needs replicas; state to run (Postgres, Redis); Python hot path can bottleneck. Shared Valkey/Redis mitigates the *per-replica state* problem (limits/cooldowns shared across gateway replicas) — module 04.
4. Client: exact request, `max_tokens`, model alias, stream or not. Gateway: log row says 200 and shows tokens — so it is not an auth/limit/route problem; `usage.completion_tokens` (0 or equal to `max_tokens`?). Response `finish_reason`: `length` with a tiny `max_tokens` or the context filled by the prompt; `stop` with 0 completion tokens means the model emitted EOS immediately (template/system prompt/stop sequences). Engine: call it directly with the same prompt; read its log (prompt truncated? n_ctx exceeded?). Infra last. Key idea: stop at the first layer that disagrees with the one above.
5. The Hebrew text uses more tokens (roughly 2-3x per word; the English 95 words is ~125 tokens, the Hebrew 120 words may be 250-350) because tokenizers are trained mostly on English text and split Hebrew words into many short pieces. Limits and bills use tokens because cost and capacity scale with tokens processed (prefill compute, KV memory, decode steps), not with characters or requests; one request can be 50 or 50,000 tokens.
6. Any three: `usage` fields differ (streaming usage not sent by default, cached-token details); tool calling (needs `--enable-auto-tool-choice` + parser in vLLM, `--jinja` in llama.cpp; response shape/arguments formatting); `max_tokens` vs `max_completion_tokens`; unsupported/ignored params (`logprobs`, `n`, `response_format`, `seed`); model-name handling (engine requires its served name); error codes and error body shape; context-length error behaviour (truncate vs 400); chat template differences; FIM `/infill` vs `/v1/completions` suffix support.
7. Spend rows are batch-written by the proxy (a queue flushed every `proxy_batch_write_at` seconds; lab: 5 s, default much longer). Lowering the interval increases DB write frequency/load on Postgres and lock contention under high QPS; raising it makes budgets/limits enforced on stale spend and dashboards lag. (Rate limits themselves use in-memory/Redis counters, not the DB.)
8. The host is internet-facing: binding `0.0.0.0` would expose the gateway (and the master key's blast radius) to the internet. Loopback only; reach it through Tailscale (`100.127.87.65:18040`, UIs are bound there too in the lab) or an SSH tunnel (`ssh -L 18040:127.0.0.1:18040 host`).
9. (a) The gateway: key/team/model RPM or TPM limit (LiteLLM 429 with a rate-limit message and headers; the gateway log has the denial; the engine log has no matching request). (b) The engine or something in front of it: saturated queue/`--max-num-seqs`/deferred requests answered with 429/503 by the engine or an ingress; gateway log shows an upstream error and the engine log shows the rejection; also an upstream provider's own 429. Tell apart by the response body/headers, which component's log has the line, and whether the engine's `/metrics` shows it saturated.
10. May: HTTP/SSE/tokens/usage semantics, slots/batching/prompt-cache counters and how to read them, quantisation sizes, gateway behaviour (limits, routing, accounting), request-level debugging ladder. May not: GPU throughput/latency numbers (CPU is compute/bandwidth-limited differently), VRAM/KV capacity or OOM behaviour, TP/NCCL behaviour, model quality or tool-calling reliability of 0.5B models, and vLLM-specific scheduler behaviour (preemption, PagedAttention).

## Common mistakes
- Putting Postgres in L4 ("it's infrastructure"): the layer is decided by whose state it is.
- Forgetting `-N` with curl, then concluding the stream is not streaming; or counting the `[DONE]` line and the usage chunk as content chunks.
- Counting `usage` from a stream that did not set `include_usage` (field absent).
- Using the backend's model name instead of the alias (`model: "chat"`), or the alias in the engine call.
- "Fixing" the coder alias by pointing it at the chat engine: the 200 passes but the traffic went to the wrong backend (verify checks the engine counters).
- Searching the spend log right after the request without waiting for the batch flush.
