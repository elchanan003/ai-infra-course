# 01 — Tutor answers

## Quiz
1. Decode: each step produces one token per sequence but must read all weights (and that sequence's KV) from HBM: ~1-2 FLOPs per byte read, far below the GPU's FLOPs/bandwidth ratio (~300 on an H100) → bandwidth-bound; it determines ITL. Prefill: all P prompt tokens share each weight read (arithmetic intensity ~P) → compute-bound; it determines TTFT (with queueing). Batching decode shares the same weight read across all sequences, so aggregate tokens/s rises almost linearly until compute-bound while per-step time grows slowly; prefill is already compute-bound, so batching prompts adds almost no efficiency.
2. KV/token = 2 x 32 x 8 x 128 x 2 B = 131,072 B = 128 KiB. 16 x 8192 = 131,072 tokens → 131,072 x 131,072 B = 17,179,869,184 B = **16 GiB**.
3. MHA: 4x → 512 KiB/token (64 GiB for the 16 x 8k case). FP8 KV: half → 256 KiB/token (32 GiB). (GQA + FP8 KV: 64 KiB/token, 8 GiB.)
4. Weights 7.62e9 x 2 B = 15.24e9 B = 14.19 GiB. Budget 24 x 0.9 = 21.6 GiB; minus 14.19 minus 2 = **5.41 GiB** for KV. KV/token = 2 x 28 x 4 x 128 x 2 = 57,344 B (56 KiB). 5.41 GiB = 5.81e9 B → ~101,300 tokens → 101,300 / 4096 = 24.7 → **24 sequences** (accept 24-25).
5. KV needed for one max-length sequence = 65,536 tokens x bytes/token (here 24,576 B) = 1.5 GiB (65,536 x 24,576 = 1.61e9 B); the pool is 1.0 GiB → holds ~43,690 tokens (vLLM reports a rounded block-aligned number, e.g. 43,520), so even one full-length request could not be admitted; vLLM fails at startup instead of at the first long request. Fixes: lower `--max-model-len` to the estimated maximum or below; give the KV pool more memory (higher `--gpu-memory-utilization`, free other memory on the GPU, `--kv-cache-memory-bytes`, `VLLM_CPU_KVCACHE_SPACE` on CPU); quantise KV (`--kv-cache-dtype fp8`); shard with TP; smaller/quantised weights (frees memory for KV); a bigger GPU. Wrong answer: "increase swap".
6. Weight quantisation does not change KV size (KV dtype is a separate setting, default = model dtype). It reduces weights, freeing memory that *can* be used for KV, but the per-token KV cost is unchanged. To reduce KV: FP8 KV cache (`--kv-cache-dtype fp8`), fewer/shorter sequences (`max_model_len`, concurrency), a GQA/MLA model, prefix sharing, TP (per-GPU share), sliding-window models.
7. Static: the batch of 4 runs until the 2000-token generation finishes; the three short ones finish after 50 steps but their slots idle for 1950 steps, and new arrivals wait for the entire batch. Continuous: after 50 steps the finished sequences leave and waiting requests join at the next iteration; GPU stays full. Chunked prefill: a long incoming prompt is split into chunks processed alongside decode steps under the per-step token budget, so running streams do not stall for the full prefill (bounded ITL spike) and TTFT of the long request is slightly higher.
8. `-c` is divided among slots in the classic layout: 4096/8 = 512 tokens per slot. A 1500-token prompt exceeds the slot context: truncated or rejected ("prompt too long"/context error). Fixes: `-np 2` (2048 per slot) or `-c 12288 -np 8` (1536 per slot, 8 concurrent) — i.e. make `c/np ≥` longest prompt + generation; or fewer parallel slots; newer `--kv-unified` shares the buffer. Verify with `/slots` `n_ctx`.
9. B hits (prefix [S][D] identical, only q2 differs) — it reuses the cached KV for S and D and prefills only q2. C misses: the timestamp at position 0 changes the first tokens, so nothing after it matches (strict prefix). Rule: stable content first, volatile content (timestamps, ids, questions) last; deterministic serialisation.
10. Prefix cache is per replica; round-robin sends each request to a random replica, so a given prefix is cached on only the replicas that happened to see it (after warmup each replica has it, but eviction, uneven traffic and different cache pools lower the rate; the first request per replica always misses; with low traffic per prefix ~1/N). Fixes: prefix/KV-aware routing (llm-d, vLLM production-stack router, Gateway API Inference Extension), consistent hashing on a prompt-prefix key / session affinity, fewer larger replicas (higher TP) for cache-heavy workloads.
11. TP must divide the attention heads (64) and should divide KV heads (8): valid {1, 2, 4, 8} (1 does not fit for FP16). TP=3: 64 % 3 ≠ 0 and 8 % 3 ≠ 0 → invalid. TP=16: divides 64 but exceeds 8 KV heads → KV heads would be replicated (no KV saving per GPU), it needs 2 nodes (TP over InfiniBand is slow) → use TP=8 or TP=4 x PP / replicas.
12. Weights 70e9 x 2 = 130.4 GiB. Usable 2 x 80 x 0.92 = 147.2 GiB. KV pool = 147.2 − 130.4 − 4 = 12.8 GiB. 8192-token sequence = 8192 x 320 KiB = 2.5 GiB → 5.1 → **5 sequences** (marginal). FP8 weights: 65.2 GiB → KV pool 78 GiB → 31 sequences (and FP8 KV would double that).
13. TTFT p95 (and its parts: queue time, prefill time) first; "starts slowly" = TTFT. High TTFT: queueing (KV full / `max_num_seqs` reached / preemption), long prompts (prefill), cold prefix cache, a gateway/network delay. ITL p95 second (decode slowness: batch too large, long contexts, noisy neighbours/throttling). The average hides the split.
14. 3.35e12 / 16e9 ≈ **209 tok/s** (ceiling, ignores KV reads and overheads). Batch 32: weights are read once per step for all 32 → aggregate ceiling ≈ up to 32x (~6,700 tok/s) until compute/KV-bandwidth-bound; each stream slows slightly (ITL up) because per-step work and KV reads grow.
15. Prompt processing is compute-bound GEMM. Q8_0 uses simple 32-weight int8 blocks that map directly to the NEON dot-product (sdot) kernel; Q4_K needs unpacking nibbles and per-256 super-block scales/mins, more instructions per MAC (and, on this CPU, fewer optimised paths), so it is slower despite being smaller. Generation was bandwidth-bound in theory but noise-dominated on a small model. Lesson: smaller ≠ faster; speed depends on whether the hardware has an efficient kernel for the format (FP8 needs hardware support; W4 kernels help small batch, hurt at large batch) — benchmark on the target hardware and workload.

## Common mistakes
- GB vs GiB mixing; using 1.2x "rule of thumb" on weights instead of an explicit KV term.
- Using attention heads instead of KV heads; forgetting that `head_dim` may not equal `hidden/heads` (read config.json).
- Forgetting to multiply KV by sequences; forgetting overhead; applying `util` to weights only.
- Believing quantised weights shrink KV.
- `min_tp` returning 3 or 6 (not dividing heads), or TP > number of KV heads treated as fine.
- Judging batching by wall-clock of a single request instead of aggregate tokens per second from counters.
- Cache test with a timestamp/nonce at the start of the prompt; or reading `/slots` fields that don't exist in this build (use `usage.prompt_tokens_details.cached_tokens` / `/metrics`).
- `-c` vs `-np`: forgetting that the context is split between slots.
- Concluding "Q4 is faster because it's smaller" from one noisy generation run.
