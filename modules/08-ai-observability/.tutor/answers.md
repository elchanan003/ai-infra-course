# 08 — Tutor answers

## Quiz
1. LLM latency is split (TTFT vs ITL) and request sizes vary by orders of magnitude, saturation is KV/queue not CPU. Extra signals (any three): TTFT/ITL quantiles (user experience, not averages); tokens/s in/out (capacity, cost); KV usage (headroom before preemption); queue length / queue time (capacity shortfall); preemption rate (batch cap above KV); spend per key/team (cost, abuse); prefix cache hit rate (efficiency); finish reasons (length truncation, aborts = client timeouts).
2. TTFT = request arrival to first output token: queue wait + tokenization + prefill; felt as "thinking time". ITL = gap between consecutive output tokens: one decode step (batch size, memory bandwidth); felt as typing speed. Streaming averages hide both.
3. `histogram_quantile(0.95, sum by (le, model_name) (rate(vllm:time_to_first_token_seconds_bucket[5m])))`. `le` identifies the buckets; without it, buckets of different `le` are summed into one number and `histogram_quantile` returns NaN/nothing. Average of per-replica p95s is not the p95 of the union (replicas with few requests count as much as busy ones); aggregate the bucket rates first, quantile last.
4. Total 100, rank 99. Cumulative at 2.5 is 98 (< 99), so the quantile is in bucket (2.5, 5.0] with 98 below and 2 inside: `2.5 + (99-98)/2 x 2.5` = **3.75 s**. Weakness: interpolation assumes observations are spread uniformly inside a bucket; the real value could be anywhere in 2.5-5 s, and wide buckets (1.0 -> 2.5 -> 5) make any threshold between boundaries unreliable. Better evidence: SLO attainment `sum(rate(_bucket{le="2.5"}[5m])) / sum(rate(_count[5m]))` = 98% (exact); a 2 s threshold has no bucket boundary, so compute at `le="2.5"` (and say the SLO is violated: 98% < 99%).
5. `num_requests_waiting`: gauge, plot directly / `max_over_time`; `num_preemptions_total`: counter, `rate()`/`increase()`; `time_to_first_token_seconds_bucket`: histogram buckets, `histogram_quantile(q, sum by (le)(rate(...)))`; `kv_cache_usage_perc`: gauge, 0..1 fraction, unit percentunit, `max by` across replicas.
6. First: `rate()` on a gauge: gives derivative-like per-second change (zero when stable) and is semantically wrong; plot the gauge. Second: unit is "percent (0-100)" but the value is a 0..1 fraction; use `percentunit` (or multiply by 100).
7. Window ≥ 4 × scrape interval (≥ 20 s; practical `[1m]` or `$__rate_interval`). `[10s]` contains at most 2 samples (often 1 with jitter): `rate()` returns nothing/gappy values; `histogram_quantile` noisy.
8. e.g. `sum by (model_name) (vllm:num_requests_waiting) > 5` for 3m (or `deriv(...[5m]) > 0` combined with a floor), severity warning; page only if TTFT also breached. False positive: a burst that clears within a minute — handled by `for`; or a long-prompt batch job; or a replica restart (metrics reset) — add `up == 1`. Accept reasonable variants with a justified threshold.
9. A KV cache that fills is the engine using memory as designed (prefix cache and long-lived blocks); 90% with no queue and no preemptions is healthy. Re-scope: fire only when KV > 0.9 AND (waiting > 0 OR preemption rate > 0) for a few minutes; page on TTFT symptom; keep plain KV% on the dashboard.
10. (a) The metric was removed/renamed (`kv_cache_usage_perc`), so the expression is empty and never errors; (b) 0..1 vs percent threshold mix-ups are the other classic. Guard: `absent(vllm:kv_cache_usage_perc)` alert or `up`/`count({__name__=~"vllm:.+"}) == 0`, plus promtool tests and a "metric exists" check in CI.
11. 6% vs engine but only 0.3% vs gateway counters: the Postgres spend path is close to the gateway; the 6% gap to the engine is traffic that never went through the gateway (direct calls, benchmarks, health probes, internal tools), or gateway cache hits (the other direction), retries (engine counts twice). Check order: (1) flush barrier/lag (spend logs batch) — ruled out mostly by the 0.3% match; (2) bypass traffic (engine requests with no gateway counterpart: compare request counts / client ips); (3) counter resets/restarts; (4) tokenizer differences (usually < 1-2%); (5) failed/aborted requests. Suspect bypass first.
12. Spend logs are batch-written asynchronously: right after load the table under-reports. Lab: `proxy_batch_write_at: 5` (seconds). Production default is around one minute (60 s), so reconciliation windows must be longer and end before now minus the lag.
13. Precomputed series: cheaper dashboards/alerts, stable names, consistent definitions across teams; evaluation at fixed interval. Trap: a recorded p95 can't be re-aggregated across labels (avg of p95s is wrong) — record the `sum by (le, ...)` rate if you need flexible aggregation; also the series name is an API, and quantile recorded per replica then averaged is wrong.
14. Components: langfuse-web, langfuse-worker, Postgres, ClickHouse, Redis (queue), S3 blob store. Path: LiteLLM callback -> web API -> event batch written to S3 and job enqueued in Redis -> worker processes -> writes ClickHouse (and metadata in Postgres) -> UI/API query ClickHouse. Ingestion is async (seconds); tests poll the public API with a timeout (e.g. up to 30-60 s) instead of asserting immediately.
15. Full prompts and responses (including code, pasted secrets, PII), metadata (user, session, tags), token usage, cost, latency, model, errors. Controls: message masking / `turn_off_message_logging`, per-project access control & SSO, retention/TTL on ClickHouse/S3, sampling, network isolation (self-host), redaction at the gateway. Accept any two.

## Common mistakes
- Dashboard JSON referencing a datasource by name/uid that does not exist in provisioning.
- `histogram_quantile` fed with `rate()` of `_sum`; quantile over a window shorter than 4x scrape.
- Prometheus not reloaded after editing rules (or invalid YAML silently keeps old rules): use `promtool check rules`, then reload and check `/api/v1/rules`.
- Using `/metrics` instead of `/metrics/` for LiteLLM without following the 307 redirect (target down or 307 in logs).
- Reconciling before the flush barrier; comparing different windows for Prometheus and spend logs (use the same start/end).
- Langfuse asserted before async ingestion (needs polling).
